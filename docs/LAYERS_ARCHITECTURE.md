# Архитектурный подход и разделение по слоям

В данном документе описаны ключевые принципы архитектуры проекта, структура слоев и правила разработки, которыми необходимо руководствоваться при расширении функционала.

## Архитектурная концепция
Проект строится на принципах **чистой модульной архитектуры**. Это означает:
*   **Независимость модулей**: Функциональные модули (фичи) не должны зависеть друг от друга напрямую.
*   **Инверсия зависимостей (DIP)**: Высокоуровневые модули не зависят от низкоуровневых. Все компоненты взаимодействуют через абстракции (интерфейсы).
*   **Единая точка входа**: Сборка всех модулей и конфигурация зависимостей происходит на уровне приложения (`App Layer`).

---

## Разделение по слоям

### 1. Слой приложения (App Layer)
**Путь:** `lib/app/`
Верхнеуровневый слой, который знает обо всех остальных слоях.
*   **Назначение**: Инициализация приложения, глобальная конфигурация DI, оркестрация навигации.
*   **Main**: Точки входа (`main_dev.dart`, `main_prod.dart`).
*   **DI**: Регистрация зависимостей, специфичных для всего приложения.

### 2. Слой ядра (Core Layer)
**Путь:** `lib/core/`
Базис проекта, предоставляющий общие сервисы и инфраструктуру. Не зависит от функциональных модулей.
*   **Networking**: Реализация API-клиента, обработка сетевых ошибок.
*   **Storage**: Локальные базы данных (Drift), защищенное хранилище (Secure Storage).
*   **Routing**: Общие интерфейсы навигации для кросс-модульного взаимодействия.
*   **DI**: Базовые модули инъекции зависимостей.
*   **Logging**: Системы мониторинга и логирования.

### 3. Функциональный слой (Features Layer)
**Путь:** `lib/features/`
Независимые бизнес-модули приложения.
*   **Структура модуля**: Каждый модуль внутри может делиться на `data`, `domain` и `presentation` (если это требуется для конкретной сложности задачи).
*   **Автономность**: Модуль может быть выделен в отдельный пакет без изменения остального кода.
*   **Взаимодействие**: Для перехода во вне или использования общих сервисов фича обращается к абстракциям из `Core Layer`.

## Правила разработки

### 1. Управление зависимостями (DI) и памятью
*   **Ограниченное использование `@singleton`**: Используйте синглтоны только для глобальных сервисов инфраструктуры, которые должны жить всё время работы приложения (например, `AppDatabase`, `BaseApiClient`, `SessionObserver`).
*   **Избегайте утечек памяти**: Не храните состояние фич или тяжелые данные в синглтонах. Для бизнес-логики (BLoC, UseCases) и репозиториев фич предпочтительнее использовать `@injectable`, чтобы объекты корректно уничтожались, когда они больше не нужны.
*   **Работа с ресурсами**: Всегда закрывайте стримы и очищайте кэши при уничтожении компонентов.
*   **Разделение интерфейса и реализации**: Регистрируйте реализацию под типом интерфейса для упрощения тестирования и замены:
    ```dart
    @Singleton(as: BaseService)
    class ServiceImpl implements BaseService { ... }
    ```

### 2. Обработка ошибок (Error Handling)
*   Никогда не прокидывайте исключения сторонних библиотек (например, `DioException`) в UI-слой.
*   Маппите все технические ошибки в доменные исключения на уровне репозитория или API-клиента.
*   Централизованно обрабатывайте критические ошибки сессии (401) через `SessionObserver`.

### 3. Навигация
*   Конкретные маршруты описываются внутри фич.
*   Межмодульные переходы осуществляются через интерфейсы `BaseFeatureNavigation` в `Core`.
*   Логика «склейки» (подбор нужного маршрута по запросу) выносится в `App Layer`.

---
*Данные правила являются обязательными для соблюдения. При внесении изменений в архитектурный подход документ должен быть обновлен.*
