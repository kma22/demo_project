# Сетевой слой: ApiClient и Обработка ошибок

Документация описывает архитектуру сетевого взаимодействия приложения, построенную на базе пакета `dio`.

## Ключевые компоненты

### 1. ApiClient (Implementation)
**Путь:** `lib/core/api_client/src/api_client.dart`
*   **Роль**: Универсальная обертка над инстансом `Dio`.
*   **Ответственность**: 
    *   Выполнение HTTP-запросов (GET, POST, PUT, DELETE).
    *   Централизованный маппинг ответов и типизация.
    *   Трансформация исключений библиотеки `Dio` в доменные исключения приложения.

### 2. BaseApiClient (Interface)
**Путь:** `lib/core/api_client/src/base_api_client.dart`
*   **Роль**: Контракт сетевого клиента.
*   **Назначение**: Позволяет репозиториям зависеть от абстракции, а не от конкретной реализации, что упрощает подмену клиента (например, для мокирования в тестах или перехода на другую библиотеку).

### 3. SessionObserver
**Путь:** `lib/core/api_client/src/session_observer.dart`
*   **Роль**: Глобальный наблюдатель состояния сессии.
*   **Функции**:
    *   Предоставляет `Stream<void>` для подписки на события истечения сессии.
    *   Служит мостом между сетевым слоем (интерцептором) и UI-слой (для автоматического редиректа на экран логина).

### 4. Инициализация (DioModule)
**Путь:** `lib/core/api_client/src/di/dio_module.dart`
*   **Роль**: Фабрика для настройки и регистрации `Dio` в DI-контейнере.
*   **Настройка**: 
    *   Установка глобальных таймаутов (по умолчанию 30с).
    *   Настройка базового URL из `EnvironmentData`.
    *   Сборка цепочки интерцепторов.
*   **Связь с SessionObserver**: При инициализации `OauthInterceptor` получает коллбэк, который триггерит `SessionObserver.emitSessionExpired()`, обеспечивая реактивную реакцию на потерю авторизации.

## Обработка исключений (Error Handling)

Приложение реализует многослойную обработку сетевых ошибок:

1.  **Трансформация (Mapping)**: Все `DioException` перехватываются и преобразуются в специализированные классы (например, `BadRequestException`, `UnauthorizedException`, `ConnectionException`). Это избавляет Domain-слой от зависимости от `dio`.
2.  **Парсинг Body**: Клиент пытается извлечь человекочитаемое сообщение об ошибке и внутренний код ошибки из тела ответа сервера.
3.  **Типизация**: При несоответствии формата данных ожидаемому типу `T` выбрасывается `InvalidDataException`.

## Преимущества подхода

*   **Независимость от библиотеки**: Бизнес-логика не знает об использовании `dio`.
*   **Автоматизация Auth-процессов**: Инкапсуляция логики обновления токенов избавляет разработчика от необходимости обрабатывать 401 ошибку вручную в репозиториях.
*   **Предсказуемость**: Единая точка обработки ответов гарантирует, что все сетевые ошибки будут обработаны по единому стандарту.
