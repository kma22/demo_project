# Архитектура Навигации

Документация описывает структуру системы навигации, спроектированную для работы в многомодульном проекте.

## Структура слоев

### 1. Слой приложения (App Layer)
**Путь:** `lib/router/`
**Компонент:** `AppRouter`
*   **Роль**: Выступает в качестве оркестратора.
*   **Зависимости**: Импортирует сгенерированные маршруты из всех функциональных модулей (features) и собирает их в единую карту навигации.
*   **Причина размещения**: Предотвращает циклическую зависимость `Core -> Features -> Core`. Находится выше всех фич в иерархии зависимостей.

### 2. Слой ядра (Core Layer)
**Путь:** `lib/core/routing/`
**Компоненты**: `BaseFeatureNavigation` (интерфейс), `FeatureNavigationExtension`.
*   **Роль**: Описывает абстракции для кросс-модульного взаимодействия.
*   **Интерфейсы**: Позволяют фичам инициировать навигацию к экранам других модулей, не имея прямой зависимости от них (Dependency Inversion).

### 3. Функциональные модули (Features)
*   **Роль**: Описывают собственные маршруты.
*   **Взаимодействие**: Используют интерфейсы из `Core` для переходов вовне.

## Уровни доступа и видимости

Архитектура построена на четком разграничении областей видимости для предотвращения циклической связности:

### 1. Слой `Routing` (находится в `Core`)
*   **Видимость**: Этот слой доступен абсолютно всем модулям проекта (Features, App Layer).
*   **Ограничение доступа**: Сам слой `Routing` **ничего не знает** о конкретных фичах и экранах. Он содержит только абстрактные контракты (интерфейсы).
*   **Назначение**: Служит "общей шиной" для инициации навигационных событий. Любая фича может вызвать метод из `BaseFeatureNavigation`, не имея зависимости от целевого модуля.

### 2. Слой `Router` (находится в `App Layer`)
*   **Видимость**: Является вершиной иерархии зависимостей. **Никто в проекте не знает** о существовании этого слоя и класса `AppRouter`.
*   **Область знаний**: Это единственное место в приложении, которое **знает обо всех фичах** и имеет доступ к их внутренним маршрутам.
*   **Назначение**: Выполняет роль связующего звена (Glue Code), сопоставляя абстрактные вызовы из `Routing` с конкретными реализациями страниц.

## Фундамент для полной модульности

Текущее разделение на `Routing` и `Router` является заделом под физическое разделение проекта на независимые Dart-пакеты (Packages):

1.  **Независимость сборки**: Так как фичи зависят только от `Core (Routing)`, их можно выносить в отдельные репозитории или пакеты. Они будут успешно компилироваться, так как им не нужен доступ к `AppRouter` для навигации "вовне".
2.  **Параллельная разработка**: Группы разработчиков могут работать над разными модулями, расширяя `BaseFeatureNavigation` в `Core` и не конфликтуя в файлах основного роутера.
3.  **Оптимизация компиляции**: При изменение одной фичи не требуется пересборка всех остальных модулей, так как зависимости между ними разорваны через интерфейсы в `Core`.
