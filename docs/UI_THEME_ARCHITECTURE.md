# Архитектура UI-кита и Системы Тем

Документация описывает структуру темизации, построенную на разделении контрактов, данных и логики управления.

## Структура слоев

### 1. Слой контрактов (Core Layer)
**Путь:** `lib/core/ui_kit/src/theme/`
**Компоненты:** `BaseColors`, `BaseLayout`, `BaseTextStyles`.
*   **Роль**: Определяет интерфейсы дизайн-системы.
*   **Назначение**: Позволяет UI-компонентам запрашивать семантические значения (например, `context.colors.primary`) без привязки к конкретной теме. Виджет не знает, светлая сейчас тема или темная — он просто просит «основной цвет».

### 2. Слой реализации (Implementation Layer)
**Путь:** `lib/core/ui_kit/src/theme/[colors, layout, typography]/`
**Компоненты**: `AppLightColors`, `AppDarkColors`, `AppTextStyles`, `AppLayout`.
*   **Роль**: Наполняет абстрактные контракты конкретными значениями.
*   **Сборка**: Класс `AppThemeData` маппит эти значения в нативный `ThemeData` и регистрирует их через `ThemeExtension`.

### 3. Слой управления (Management Layer)
**Путь:** `lib/core/ui_kit/src/theme/app_theme_manager.dart`
**Компонент**: `AppThemeManager`.
*   **Роль**: Оркестратор системы тем.
*   **Функции**: Инициализация темы из локального хранилища, отслеживание системной яркости через `platformDispatcher` и реактивное переключение между `light`, `dark` и `system`.

## Ключевые решения

### Работа через ThemeExtension
Вместо глобальных констант используются расширения. Это позволяет прокидывать через контекст любые кастомные параметры (цвета, отступы, пути к ассетам).
*   **Пример**: Для разных тем нужны разные логотипы — создается `AppAssetsExtension`. В `AppThemeData` для светлой темы указывается путь к черному лого, для темной — к белому. Виджет вызывает `Image.asset(context.assets.logo)`, оставаясь универсальным.

### Оптимизация производительности
Управление темой вынесено из дерева виджетов в `AppThemeManager`.
*   **Изоляция**: Менеджер сам слушает изменения системной темы (`onPlatformBrightnessChanged`).
*   **Результат**: Корневой `MaterialApp` перестраивается только при фактической смене темы. Параметры `MediaQuery` (размер окна, отступы клавиатуры) больше не вызывают полный ребилд.

### Гарантия консистентности
Использование `Base`-классов как контрактов обеспечивает строгую типизацию. При добавлении новой темы (например, `HighContrast`) компилятор потребует реализовать все токены, используемые в проекте. Это исключает ситуации «забыли покрасить кнопку в темной теме».

## Правила расширения
*   **Никакого хардкода**: Наличие Hex-кода или конкретного `FontSize` в файлах фич считается архитектурным долгом. Все значения должны быть в экстеншенах.
*   **Контракт прежде всего**: Новое свойство сначала добавляется в `Base`-класс, затем реализуется в палитрах, и только потом используется в UI.
*   **Типографика через контекст**: Шрифты всегда запрашиваются через `context.textStyles`, чтобы корректно подхватывать настройки Google Fonts и темы.
